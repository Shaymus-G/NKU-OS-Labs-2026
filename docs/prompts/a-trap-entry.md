## 2. 实现时遵守的规格（整理）

### 2.1 内存初始化迁移

- 保留 Lab3 当前接口和中断保护，不整文件替换 `pmm.c`。
- 从 DTB 读取物理范围，检查起点、长度和范围计算。
- 页描述符数组按页对齐，初始化之前检查存放空间。
- 先标记为保留，再将内核和描述符数组之后的完整空闲页登记给管理器。
- 物理范围使用当前框架已有定义推导，不固定 Lab2 的地址输出和空闲页数。

### 2.2 Trap 汇编模块

- 不修改教师 `SAVE_ALL`、`struct trapframe` 布局及 `trap()` 签名。
- RV64 下每槽 8 字节，36 槽共 288 字节。
- `a0` 传递 TrapFrame 首地址，调用 C 函数返回后 sp 回到原帧。
- 使用处理完成后的帧恢复 sstatus、sepc 及通用寄存器。
- 原始 sp 最后恢复，不再额外增加 288。
- 返回使用 `sret`；不无条件开中断，也不强制把返回模式设为 U 模式。
- 异常分类、指令长度和 EPC 推进由 B 的处理函数负责，A 不在汇编中重复实现这些策略。

## 3. AI 建议、实际采用的选择及理解

### 3.1 按保存布局实现恢复

AI 提供的草案使用 t0/t1 读取槽位 32、33，分别写回 sstatus、sepc，再恢复通用寄存器，最后恢复 x2。本人按这一方案修改实际文件，并提供完整 `git diff` 核对，不将汇编模块编译成功直接当作运行正确。

结合源码和实验，整理后的理解是：t0/t1 的原值已在槽位 5、6，因此可以暂时搬运 CSR，之后再恢复；sp 始终作为帧基址使用，直到最后一条加载完成。x0 恒为零，不需要恢复。cause 和故障地址用于诊断，不需要为了“对称”而把所有保存的 CSR 都写回。

**我：** 我需要验证恢复顺序是否真的有效，而不只是看到编译成功。尤其是 sp 提前恢复会改变后续加载地址，这一项应该有现场证据。

**AI：** 在 `__alltraps` 保存原始 sp，再在 C 入口检查帧首地址和 288 字节差值；在 `__trapret` 检查 C 返回后的 sp；最后停在 sret 前比较恢复出的 sp 和帧中原值。这样可以把保存、传参和恢复三个阶段联系起来。

### 3.2 最小迁移而非扩展实验范围

实际保留 `default_pmm_manager`。Best-Fit 必要迁移交由 B 完成，本次没有把 Lab2 Buddy/SLUB 搬入 Lab3。原因是 A 当前任务是保证内存初始化与 Trap 路径正确，额外扩展会增加依赖和共同分支冲突。

在协作上，本人明确继续共同使用 `lab3`，按文件职责划分修改范围，并将阶段成果、验证边界和后续依赖整理成交接文档。

### 3.3 通过比较建立验证依据

调试不是只打印寄存器后判断“看起来正常”。本次使用便利变量保存入口值，再比较 TrapFrame 字段；在 C 处理返回后保存目标值，再比较实际恢复寄存器和返回 PC。比较结果为 1，才支持对应字段一致的结论。

## 4. 实际遇到的问题与处理

### 4.1 旧宏在 Lab3 中不存在

初版迁移建议遗漏了宏依赖差异。本地执行目标文件编译后，实际报错：

```text
error: 'PHYSICAL_MEMORY_END' undeclared
error: 'KERNEL_BEGIN_PADDR' undeclared
```

本人将错误反馈，并据修正建议在 `page_init()` 内使用 Lab3 已有常量计算：

```c
const uintptr_t kernel_begin_pa =
    (uintptr_t)KERNBASE - (uintptr_t)PHYSICAL_MEMORY_OFFSET;
const uintptr_t physical_memory_end =
    kernel_begin_pa + (uintptr_t)KMEMSIZE;
```

当前对应 `0x80200000` 和 `0x88000000`。实际管理末端仍需要与 DTB 范围比较并按页对齐，没有将 DTB 查询替换成硬编码内存大小。

重新编译后，pmm 模块成功，trapentry 目标文件已是最新，管道在启用 `pipefail` 后返回 0。此处修复依据来自编译器和当前源码，说明 AI 的初始建议也必须经过工程验证。

### 4.2 局部编译与完整验收的区别

B 的处理函数尚未就绪时，先编译 A 的两个目标文件，避免为消除整工程错误去改动队友职责范围。B 推送后，再执行普通运行、教师评分和 GDB 检查。

这种分阶段验证使问题归属更明确：局部编译检查接口和语法，联合运行检查执行路径，GDB 检查保存与恢复的中间状态。

### 4.3 GDB 停点名称与返回后的 CSR

本次执行 `tbreak *trap` 后，GDB 显示的源代码位置是 `trap_dispatch`。该现象与优化、内联和调试行号映射相容，不能仅凭函数显示名判断入口调用错误。实际检查到 a0 与 sp 相同，帧大小和保存字段均符合布局。具体优化形式需要结合反汇编确定，不作未经核验的断言。

单步 sret 后，PC 已回到原来的内核循环，但 scause 和 sepc 仍保留先前值。sret 不负责清空它们，因此不能据此判断发生了新的中断。本次以实际 PC、所在指令和返回目标比较确定已经返回。

### 5.3 恢复与返回验证

在 `__trapret` 检查到 sp 返回原帧，处理后的 EPC 仍为 `0xffffffffc020009c`。随后按本次反汇编，在 `0xffffffffc0200c9e` 的 sret 前设置临时断点：

- sepc 与返回目标一致。

- 单步 sret 后 PC 为 `0xffffffffc020009c`，与保存的返回目标比较为 1。
- 当前指令为 `kern_init` 中循环到自身的跳转，说明已经返回普通内核执行位置。

这些地址来自本次构建，不能作为未来构建的固定断点地址。
